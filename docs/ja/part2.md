# 必須の実践課題 2 題

所要時間：25 分・経過時間：30〜55 分

どちらも Explorer のモードで取り組みます。シナリオは架空です。実際に得た回答と出典を記録してください。理由が適切であれば、候補が異なっても構いません。製品のデプロイや顧客の認証情報の入力は行いません。

## 課題 1：文書を使う問い合わせ支援 {#exercise-1}

12 分・経過時間：30〜42 分

あるソフトウェアパートナーが、小売業の顧客との初期検討に使うデモを考えています。店舗の担当者が、承認済みの商品資料や規程から回答を探せるようにしたいという課題です。本番導入はまだ決まっていません。回答には出典を示し、資料に根拠がなければ答えられないと伝えることを求めています。

### ステップ 1：探索の会話を始める

Explorer のモードで新しい会話を始め、貼り付けます。

```text
私は Build Sales で、Building Blocks は初めてです。架空のソフトウェア
パートナーが、小売業向けの初期検討用デモを準備しています。店舗担当者が
承認済みの商品資料や規程から回答を得て、その出典を確認したいという課題です。
根拠がなければ、回答できないと伝える必要があります。
現在のカタログツールを使ってください。確認質問は最大 2 つ、1 回に 1 つずつ
聞いてください。Building Blocks の候補を最大 2 つ挙げ、業務の言葉で理由を
説明し、出典の URL と検証すべき点を 1 つずつ示してください。
スキルのインストール、モードの変更、デプロイは行わないでください。
```

質問された場合の回答例：利用者は店舗担当者、入力は架空の PDF やテキスト文書、成功の目安は出典付きの回答または明確な「見つからない」という回答です。実際の顧客情報は追加しません。

### ステップ 2：提案候補を確かめる

両方の候補のリンクを開き、README の目的、提供される資産、前提条件を読みます。Explorer のリンクが古い場合は、[現在の上流の概要](https://github.com/ibm-self-serve-assets/building-blocks)から該当するページを探し、元のパスと参照し直したパスを記録します。確かめられなければ「未確認」とします。

続けて質問します。

```text
出典に明記されていることと、推測したことを分けてください。
候補ごとに、提供される資産と前提条件を 1 つずつ示してください。
カタログと README が食い違う場合は、その違いを確認事項として残してください。
測定していない ROI や、本番利用できることを断定しないでください。
```

### ステップ 3：結果を記録する

ワークシートへ次の項目を記録します。

| 項目 | 書くこと |
|---|---|
| 業務課題 | 店舗担当者の困りごとを 1 文で書く |
| 候補 1・候補 2 | 名前と、その候補が役立つ理由 |
| 根拠 | 出典 URL、確認日、実在する資産または明記された機能 |
| 確認事項 | 回答品質、権限、前提条件などの質問を 1 つ |
| 提案の説明 | 課題 → 機能 → 次の検証を 30 秒で話す内容 |

??? example "考え方の例：固定の正解ではありません"
    文書から根拠を探す候補として RAG、対話画面や作業の流れを扱う候補として Agent Builder が考えられます。組み合わせればそのまま動くと決めつけず、現在の README を確認します。「正しい規程を引用するかを検証したい」は次の確認事項になります。「必ず正確に回答できる」は、この演習では裏付けられません。

    現在の入口：[RAG](https://github.com/ibm-self-serve-assets/building-blocks/tree/main/data/pipelines/rag)、[Agent Builder](https://github.com/ibm-self-serve-assets/building-blocks/tree/main/ai/agents/agent-builder)。

完了の目安は、候補 2 つを説明し、根拠を示すか未確認と記録し、次の検証を挙げられることです。古いカタログ項目を発見したことも観察結果です。動く資産を想像で補わないでください。

## 課題 2：秘密情報管理の検討をエンジニアへ引き継ぐ {#exercise-2}

13 分・経過時間：42〜55 分

架空のパートナーが、デモを作るたびに接続用スクリプトへ認証情報をコピーしています。秘密情報と機械のアクセスを繰り返し管理できる方法を検討したいという相談です。今回はエンジニアとの初期検討を準備します。システムの変更や認証情報の更新は許可されていません。

### ステップ 1：課題に合う機能を比較する

課題 1 の記録を残し、新しい会話を始めます。

```text
私は Build Sales の初心者です。架空のパートナーが、デモ用の接続スクリプトへ
認証情報をコピーしており、秘密情報と機械のアクセスを再現可能な方法で
管理したいと考えています。今回は初期検討だけを行います。
現在のカタログを使って、関連する Building Block を探してください。
確認質問は最大 2 つ、1 回に 1 つずつ聞いてください。
秘密情報や ID を扱う機能が適する理由と、文書から回答する仕組みだけでは
足りない理由を説明し、出典のリンクと前提条件を示してください。
秘密情報の要求、インストール、キーの更新、デプロイは行わないでください。
```

質問された場合の回答例：利用者はパートナーのデモ開発チーム、既存のスクリプトはテスト用 API へ接続、実際の認証情報は使いません。今日の成功は小さな検証計画への合意であり、接続の実装ではありません。

### ステップ 2：引き継ぎ資料を作る

出典を確認してから、貼り付けます。

```text
エンジニアへ渡す短い use_case_summary.md をワークスペースの直下へ作ってください。
業務課題、利用者、今回の範囲、候補と理由、確認した出典 URL、前提条件、
未解決の質問 2 つ、小さな次の検証とその成功条件を含めてください。
確認した事実と仮定を明確に分け、この架空のシナリオだけを使ってください。
インストール、サービスの設定、デプロイは行わないでください。図は任意です。
```

Bob から確認された場合は、依頼したローカル文書の作成だけを承認します。ファイルを書けない場合は、回答をワークシートへコピーしてください。文章だけでも引き継ぎは完成です。図や製品のインストールは必須ではありません。

### ステップ 3：内容を点検し、提案を話す

| 確認項目 | 完了の目安 |
|---|---|
| 課題と範囲 | 秘密情報と機械のアクセスを扱う初期検討だと分かる |
| 候補と出典 | 選定理由と読める出典がある。確認できない点は明示されている |
| 前提条件 | 出典に記載された要件がある |
| 未解決の質問 | エンジニアや顧客に確認すべき質問が 2 つある |
| 次の一歩 | 小さな検証と、観察できる成功条件がある |
| 説明の言葉 | 実装経験のない同僚も説明できる |

??? example "引き継ぎの例"
    秘密情報の管理では Vault を使う候補が考えられます。現在の [Secrets Management の README](https://github.com/ibm-self-serve-assets/building-blocks/tree/main/automation/secure/non-human-identity-and-secret-management/secrets-management)を確認します。稼働中の Vault 環境まで提供されるとは推測しません。

    未解決の質問の例は「どのシステムが ID を発行するか」「誰が秘密情報のライフサイクルを管理するか」です。次の検証として、承認された検証環境のダミーの秘密情報を使い、スクリプトへ直接書かずに取得できるか確かめる案が考えられます。これはエンジニアへ渡す計画であり、この時間内に実行する指示ではありません。

完了の目安は、引き継ぎに選定理由、根拠、未解決の質問 2 つ、次の検証があることです。ペアの方か講師へ 30 秒で提案を話してください。

- [ ] 文書を使う問い合わせ支援の候補をまとめた。
- [ ] 秘密情報管理の引き継ぎをまとめた。
- [ ] 事実と仮定を分け、確認できなかった点も記録した。
